# 백엔드 에이전트 구조: 2 에이전트 vs 1 에이전트 + 2 스킬 — 3자 토론 결론

> 토론자: claude(claude-debater)·codex(gpt-5.5)·agy(Gemini 3.5) · 진행자(중립) Claude Code · 2026-06-29 · Light 모드(반증 의무 + 정직 라벨)

## 핵심 결론

**옵션 B — 에이전트 1개(`backender`) + 스킬 2개(`spring`·`fastapi`) + `backender-checker`(checker 쌍)** 이 기본값. 3자 전원 동의(B/신뢰도: in-scope 上 ~ 中).

> **결정룰 한 줄**: **지식(프레임워크) 차이 → B / 역할 판단·권한·checker 기준이 반복적으로 갈리거나, 도구권한이 하드 보안경계거나, 한 세션이 多스택을 오가거나, N이 영구 2 고정 → A.**

축: **에이전트 = 역할(안정축, "누가") / 스킬 = 교체 가능한 지식(변하는축, "무엇으로")** → 변하는 축(스택)을 *교체 가능한 층(스킬)*에 둔다.

## 왜 B인가 (정리)

| 근거 | 내용 |
|------|------|
| **역할 단일 정본** | backend 역할 로직(요구 해석·변경범위·테스트/마이그레이션 판단·리뷰대응·보안·보고)은 스택 무관 동일 → 1곳 작성, 드리프트 0. A는 역할 로직을 두 에이전트에 복제. |
| **컨벤션 정합** | "에이전트=역할, 스킬=지식" 그대로. |
| **확장성** | 스택 N개 = 에이전트 1 + 스킬 N(`django`·`nestjs`…). A는 에이전트(+checker) N개. |
| **컨텍스트 효율** | 그 프로젝트 스택 스킬만 온디맨드 로드. |
| **checker 단순** | `backender-checker` 1개가 공통 품질기준 유지(필요 시 스택 검증 스킬 호출). |

## A가 맞는 예외 (반대 옵션 조건)

- 스택별로 **역할 판단·운영 책임·품질 기준·실패 모드·checker가 실제로 다를** 때(프레임워크 지식이 아니라 *역할/거버넌스* 차이).
- 도구·배포·시크릿 권한이 **하드 보안경계**라 에이전트 수준 격리가 필요할 때.
- 한 세션이 **여러 스택을 오가**거나(예: monorepo), 스택→스킬 바인딩이 **재량적**일 때.
- N이 **영구 2 고정**이고 공통 워크플로우 공유 필요가 없을 때.

## ⚠️ B의 전제 = 결정론적 바인딩 (행동 항목)

B의 안전성(스택 관용구 혼입 0)은 **"backender가 어느 스킬을 쓸지가 결정론적으로 고정"**된다는 데 의존한다. *희망이 아니라 강제*해야 한다:
1. **project-init**이 각 repo `CLAUDE.md`에 **stack → skill**을 못박는다(예: "이 repo는 Spring → `spring` 스킬만").
2. **스킬 frontmatter에 hard stack-guard**("타 스택 관용구 금지").
> 이 강제가 있으면 신뢰도 上, 없으면 中으로 하향(혼입 리스크가 실재화 → A 경쟁력 상승).

## 검증 원장

| 주장 | 판정 | 근거 |
|------|------|------|
| 에이전트=역할·스킬=지식, maker-checker 쌍 필수 | ✅ 확정 | workflow.md §9·원칙12 |
| 위키 5스킬이 per-vault CLAUDE.md로 vault 안 섞고 동작(1세트 = 다(多)컨텍스트) | ✅ 확정 | 실제 운영 선례(emotion/dakman/chagok-wiki CLAUDE.md) — B 구조의 **존재증명** |
| 동일 backend 역할 로직은 스택 무관 → A는 복제·드리프트 | ✅ 확정(논리) | 역할 정의상 |
| "에이전트/checker 폭발 = 거버넌스 붕괴" | ❌ 교정 | held-out 종결 게이트(교차모델 3인/fresh)는 **스택 수 무관 A·B 둘 다 1개** → A의 약점은 *등록·드리프트 오버헤드*지 거버넌스 붕괴 아님 |
| "백엔드 공통규칙 80% 유사" | ⚠️ 미검증 | 출처 없는 정밀수치(수사). 결론의 load-bearing 아님 |
| `@Transactional`(Spring thread-bound) vs FastAPI(async event-loop, session-per-task) 기본값 뒤집힘 | ⚠️ 추론 | 프레임워크 설계상 알려진 사실이나 본 토론서 오라클 실행검증 안 함. 판정: *역할 판단 분기는 맞으나* repo 컨텍스트 고정 + 스킬 stack-guard로 통제 → **A로 밀지 않고 B 위 설계조건**으로 강등(claude 자기 prosecutor 강등, 3자 합의) |
| 신뢰도 上 vs 中 | ⚠️ 잔여 이견 | 범위 해석 차 — **in-scope(별 repo 2개, working-dir가 스택 고정) = 上**(claude) / 혼입 리스크 hedge = 中(codex·agy). monorepo·교차스택 세션이면 中~A 재평가 |

## 잔여 이견 (지우지 않음)

- **신뢰도**: claude 上(in-scope) ↔ codex·agy 中. 핵심 변수 = "stack→skill 바인딩이 결정론이냐 재량이냐". 결정론 강제(위 행동항목) 시 上으로 수렴 가능.
- 따라서 결론은 **"B + 결정론적 바인딩 강제"**가 한 묶음. 바인딩이 보장 안 되면 신뢰도 하향·A 재검토.

## 메타 주의

claude·codex·agy 모두 LLM(2개는 Gemini/GPT 계열, 1개 Claude) → 실패 모드 상관. 본 결론은 **위키 선례(실제 운영 = 비-LLM 오라클에 준함)**에 정박했고, `@Transactional` 분기는 코드 실행으로 검증하지 않았다(추론 라벨 유지). "3자 합의"가 곧 정답 보증은 아니다.
