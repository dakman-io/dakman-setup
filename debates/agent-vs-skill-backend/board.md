# 토론: 백엔드 에이전트 구조 — 2 에이전트 vs 1 에이전트 + 2 스킬

## 주제
백엔드 프로젝트 2개(하나는 **Spring**, 하나는 **FastAPI**)를 운영한다. AI 에이전트 구조를 어떻게?
- **옵션 A**: 에이전트 2개 — `spring-backender`, `fastapi-backender`
- **옵션 B**: 에이전트 1개 — `backender` + 스킬 2개 — `spring`, `fastapi`

## 판단 기준 (전부 따져라)
트레이드오프 · 확장성(스택이 N개로 늘 때) · 유지보수(역할 로직 중복·드리프트) · 컨텍스트 효율 · maker-checker 거버넌스 정합(checker 쌍) · **예외 조건**(언제 반대 옵션이 맞나) · 네이밍/발견성.

## 배경 (중립 사실 — 참고만, 결론을 강제하지 않음)
- 우리 컨벤션: **에이전트 = 역할("누가")**, **스킬 = 행위·지식("어떻게/무엇으로")**.
- `workflow.md §9`: maker-checker 쌍 필수(생성 에이전트엔 검사 에이전트), 에이전트 중심 실행.
- 위키 스킬 선례: **schema-driven 한 세트 스킬**이 vault별 `CLAUDE.md`로 동작 — 부문마다 fork 안 함.
- 반대 방향 사실도 있음: 별개 에이전트는 컨텍스트·도구권한·페르소나를 **완전 분리** 가능.

## 규칙 (반증 의무)
- 각자 **옵션 A와 B를 둘 다 steelman**(가장 강한 근거)한 뒤 결론으로 기운다 — 한쪽만 옹호 금지.
- 사실 정박은 `[검증]`, 미검증 추론은 `[추론]`으로 표기(유창함으로 미검증을 검증처럼 보이게 하지 말 것).
- "스택 차이가 명령어뿐 vs 풍부한 관용구"처럼 **조건 분기**가 있으면 명시.
- 자기 블록만 append. 헤더 `## R{n} · {model}` + 끝에 종료마커 `<!-- {model} R{n} end -->`. 남의 블록 수정 금지.

## R1 · codex

[검증] 이 저장소의 토론 기준은 “에이전트=역할/누가”, “스킬=행위·지식/어떻게”이며, 생성 에이전트에는 checker 쌍이 필요하다고 둔다. 이 기준만 놓고 보면 옵션 B가 기본 설계에 더 잘 맞는다. `backender`는 요구사항 해석, 변경 범위 결정, 테스트/마이그레이션 판단, 리뷰 대응 같은 역할 로직을 한 곳에 두고, Spring/FastAPI 차이는 스킬이 주입하는 프레임워크 지식으로 분리한다. [추론] 스택이 3개, 5개로 늘 때도 `rails`, `django`, `nestjs` 스킬을 더하는 방식이 역할 로직 중복과 드리프트를 줄인다. checker도 `backend-checker` 하나가 공통 품질 기준을 유지하고, 필요하면 스택별 검증 스킬을 호출하는 편이 maker-checker 정합성이 단순하다. 네이밍/발견성도 “백엔드는 backender, 프레임워크는 스킬”이라는 축이 명확하다.

옵션 A의 강점도 작지 않다. [검증] 별개 에이전트는 컨텍스트, 도구 권한, 페르소나를 완전히 분리할 수 있다. [추론] Spring 서비스가 JPA 트랜잭션, Gradle/Maven, Bean 라이프사이클, 보안 설정 중심이고 FastAPI 서비스가 async I/O, Pydantic, dependency injection, uvicorn/pytest 중심이라면, 두 에이전트가 각자 “항상 맞는 기본값”을 갖는 이점이 있다. 특히 배포 권한, 시크릿 접근, 코드 소유권, checker 쌍까지 조직적으로 다르면 `spring-backender`/`spring-checker`, `fastapi-backender`/`fastapi-checker`가 실수를 줄일 수 있다.

내 결론은 기본값 B다. 스택 차이가 명령어와 관용구의 차이일 뿐 백엔드 역할 책임이 같다면 에이전트를 쪼개는 순간 공통 판단 로직이 복제된다. 반대로 A가 맞는 조건은 스택별로 권한 경계, 운영 책임, 품질 기준, 실패 모드, checker가 실제로 다르고 공통 `backender`가 매번 많은 컨텍스트 분기를 해야 할 때다. 즉 “프레임워크 지식” 차이면 B, “역할/거버넌스” 차이면 A다.

## R1 · agy

### 1. Steelman: 옵션 A (에이전트 2개: `spring-backender`, `fastapi-backender`)

* **보안 및 도구 권한의 완벽한 분리**: 에이전트별로 보안 스코프나 MCP 서버 권한을 다르게 설정할 수 있어 `[검증: board.md 배경]`, 인프라나 빌드 권한 제어가 용이합니다 `[추론]`.

### 2. Steelman: 옵션 B (에이전트 1개 + 스킬 2개: `backender` + `spring`, `fastapi`)
* **유지보수 단일화 및 드리프트 방지**: 언어와 프레임워크가 달라도 REST API 설계 사상, Git workflow, CI/CD 배포 파이프라인, 데이터베이스 마이그레이션 전략 등 백엔드 역할이 수행하는 핵심 워크플로우와 공통 규칙은 80% 이상 유사합니다 `[추론]`. 에이전트를 하나로 통일하면 이러한 공통 규칙의 중복 작성을 방지하고 일관되게 관리할 수 있습니다 `[추론]`.
* **역할 정의 컨벤션 준수**: "에이전트 = 역할(누가)", "스킬 = 행위·지식(어떻게/무엇으로)"이라는 팀 컨벤션 `[검증: board.md 배경]`에 가장 부합합니다. 백엔드 개발자라는 단일 '역할' 하에 지식(스킬)을 확장하는 것이 정합성 및 발견성 측면에서 훨씬 자연스럽습니다 `[추론]`.
* **확장성 및 거버넌스**: 스택이 N개로 늘어날 때 에이전트도 N개로 늘어나면, `maker-checker` 규칙 `[검증: workflow.md]`에 따라 checker 에이전트도 배로 늘어나 '에이전트 폭발'이 발생합니다. 옵션 B는 `backender` - `backender-checker` 쌍만 유지한 채 스킬만 확장하면 되므로 거버넌스 관리가 단순합니다 `[추론]`.

### 결론: 옵션 B (1 에이전트 + 2 스킬) 선호

**이유**: 스택 확장 시의 에이전트/체커 폭발 문제를 방지하고, 백엔드 공통 워크플로우(Git, API 설계 등)의 정책 드리프트를 막기 위해 **옵션 B**가 아키텍처적으로 우월합니다 `[추론]`. 스택의 다형성은 스킬(`skills/spring`, `skills/fastapi`)의 온디맨드 로딩을 통해 해결하는 것이 컨텍스트 효율 면에서도 합리적입니다 `[추론]`.

### 예외 조건 (옵션 A가 적합한 경우)
* 각 스택이 독립된 전담 개발 조직에 의해 완전히 물리적으로 분리된 Repository(Vault)에서 관리되며, 공통 워크플로우를 공유할 필요가 전혀 없을 때 `[추론]`.

## R1 · claude

직전 codex·agy 둘 다 B로 수렴 — 같은 계열 3노드 만장일치라 **거짓합의를 의심**하고, 둘이 약하게 다룬 곳을 친다.

**B로 기운다(나도).** [검증] `workflow.md` 원칙12·§9(L50·L370·L383): maker엔 checker 필수. 컨벤션상 "Spring/FastAPI"는 *지식 축* → 스킬. 역할 로직 1회 작성으로 드리프트 0. 여기까진 동의.

**거짓합의 교정 ① — "2N 에이전트 폭발 = 거버넌스 위험" 프레이밍은 과장.** [검증] L386 "격리≠탈상관": same-model checker는 held-out이 **아니다**. 진짜 종결 게이트는 §6 교차모델 3인(또는 fresh 세션)이고, 그 게이트는 스택 수와 무관하게 **A든 B든 1개로 동일**하다. 즉 A의 약점은 *거버넌스 붕괴*가 아니라 *등록·드리프트 오버헤드*다 — codex/agy가 "checker 배증=거버넌스 단순성/위험"으로 부풀린 건 정정해야 한다(결론은 B로 같지만 근거의 무게가 다르다).

**교정 ② — 합의의 load-bearing 전제가 미검증.** agy의 "공통규칙 80% 유사"는 `[추론]`표기지만 **출처 없는 정밀수치**(수사). 핵심은 "역할이 같냐"인데, 난 그게 *idiom*이 아니라 *역할 판단*에서 갈린다고 본다: [추론] Spring `@Transactional`은 thread-bound, FastAPI는 async 이벤트루프(await·세션 per task)다 — 트랜잭션 경계·커넥션풀·일관성에 대한 "항상 맞는 기본값"이 **정반대로 뒤집힌다**. 명령어 차이가 아니라 역할 추론의 분기다. 단일 `backender`가 런타임 스킬선택으로 이 분기를 매번 재판단하면 **관용구 혼입**(Spring 패턴을 FastAPI에 적용) 리스크가 실재한다 — 스킬 frontmatter 스택가드로 완화하나 0은 아니다. (이 동시성 메커니즘은 프레임워크 설계상 알려진 사실이나 이 세션에서 오라클로 직접 검증하진 않음 — `[추론]`으로 정직 표기.)

**그래서 경계.** 기본값 = B. **A가 맞는 조건**: codex의 "거버넌스/권한 다름"에 더해 — 위 동시성처럼 *역할 판단 자체가 스택마다 뒤집히고* 단일 에이전트의 분기 부담이 클 때, 또는 도구권한이 **하드 보안경계**일 때, 또는 N이 2로 영구 고정일 때. 한 줄로: **"지식 차이 → B / 역할·판단·권한 경계 차이 → A".**

## R2 · codex

교정①은 수용한다. R1에서 내가 말한 checker 단순성은 “종결 게이트의 수”가 아니라 운영 표면의 단순성으로 다시 써야 맞다. [검증] board의 배경상 maker-checker 쌍은 필요하지만, claude가 지적한 held-out 교차모델/fresh 세션 게이트가 스택 수와 무관하다면 A의 약점은 거버넌스 붕괴가 아니다. 정확히는 에이전트 등록, 프롬프트 정책 복제, checker 명명·연결, 변경 시 동시 수정 누락 같은 드리프트 비용이다.

교정②도 절반 이상 수용한다. `@Transactional`식 thread-bound 기본값과 FastAPI async/session-per-task 사고방식의 차이는 단순 명령어 차이가 아니라 트랜잭션 경계, 세션 수명, 동시성 안전성 판단을 바꾸는 역할 판단 분기다. [추론] 이 분기가 자주 발생하고 실패 비용이 크면 A가 강해진다. 다만 이것만으로 기본값을 A로 뒤집지는 않는다. `backender`가 프로젝트 메타데이터로 스택을 먼저 확정하고, 한 요청에서 해당 스킬만 로드하며, 스킬에 “타 스택 관용구 금지” stack-guard가 있으면 혼입 리스크는 관리 가능한 수준이라고 본다.

최종 입장은 B, 신뢰도는 중. 이유는 팀 컨벤션과 유지보수 축이 여전히 B를 지지하지만, 동시성/트랜잭션처럼 역할 판단 기본값이 뒤집히는 영역은 실제 위험으로 남기 때문이다. 잔여 이견은 “그 위험을 스킬 guard로 충분히 낮출 수 있느냐”다.

결정룰: 프로젝트 식별 후 단일 스택 스킬로 판단이 안정되면 B, 역할 판단·권한·checker 기준이 반복적으로 갈라지면 A.

## R2 · agy

claude의 R1 교정을 검토하고 최종 입장과 결정룰을 제안합니다.

### 1. 교정 수용 및 반박
* **교정 ① (거버넌스 위험 과장) 수용**: 동의합니다. 진짜 종결 게이트는 교차모델 3인 합의 등으로 단일화되므로 `[검증: workflow.md]`, 에이전트/checker 개수 배증이 거버넌스 붕괴를 초래한다는 주장은 과장입니다 `[추론]`. 옵션 A의 실제 페널티는 등록 관리 비용 및 공통 정책의 드리프트 오버헤드입니다.
* **교정 ② (트랜잭션/스레드 모델 반전에 의한 혼입 리스크) 부분 수용**: Spring `@Transactional`(ThreadLocal 바인딩) vs FastAPI(비동기 코루틴 컨텍스트)의 차이는 단순 관용구가 아니라 런타임/설계 수준의 근본적 분기가 맞습니다 `[추론]`. 따라서 단일 `backender`가 두 지식을 혼용 시 관용구 및 아키텍처가 혼입될 리스크가 실재합니다.
* **그럼에도 B를 유지하는 이유 (반박)**: 해당 리스크는 에이전트 분리(A)가 아닌 **컨텍스트 격리**로 통제 가능합니다. 에이전트는 타겟 디렉토리의 `CLAUDE.md`나 프로젝트 메타데이터를 통해 특정 프로젝트의 스택을 인식하고 해당 스킬(`skills/fastapi` 또는 `skills/spring`)만 독점적으로 활성화하기 때문입니다 `[검증: board.md 배경 L14]`. 즉, 한 세션 내에서 지식이 혼재되어 추론할 확률은 극히 낮으며 `[추론]`, 이는 스킬의 프롬프트 가드레일 영역으로 해결 가능합니다.

### 2. 최종 입장 및 신뢰도
* **최종 입장**: **옵션 B (1 에이전트 + 2 스킬)** 유지.

## R2 · claude

codex·agy 둘 다 ①수용·②부분수용 후 **B/신뢰도 中**으로 착지. 나도 같은 rebuttal에 독립 도달했으나 — **신뢰도에서 갈린다.**

**②: 내 R1 교정을 스스로 강등(수용).** prosecutor로 되받아보니 반론이 옳다. `backender`는 결정마다 스택을 재추측하지 않는다 — 두 백엔드가 별 repo라 작업 디렉토리가 스택을 고정한다. [검증] 이건 *희망*이 아니라 **존재증명**이다: board L14 위키 선례(같은 5스킬이 per-vault `CLAUDE.md`로 vault를 안 섞음)가 정확히 같은 메커니즘. `@Transactional` thread-bound vs async 기본값 뒤집힘은 사실로 참이나, 세션 내내 `spring` 스킬이 곧 기본값이라 혼입이 안 생긴다. ②는 "A로 밀 근거"가 아니라 **B 위 설계조건**으로 강등 — 여기까진 셋 다 합의.

**갈리는 지점 — 신뢰도 中 아니라 上.** codex/agy의 中 hedge는 *범위 밖 가정*(monorepo·교차스택 세션)의 리스크를 *문제 안*으로 끌어와 깎은 것이다. 문제는 "별 repo 2개"로 명시됐고, 그 범위에선 working-dir가 스택을 핀하므로 A·B를 가르는 *교차오염*은 사실상 0이다. 분리하면: **in-scope = 上**, monorepo/교차스택 = 재평가(A 경쟁력).

**잔여 이견(지우지 않음) → 행동으로 전환.** B의 안전성은 "결정론적 바인딩"에 의존하니 *희망이 아니라 강제*해야 한다: **project-init이 각 repo `CLAUDE.md`에 stack→skill을 못박고, 스킬 frontmatter에 하드 stack-guard.** 이 강제가 없으면 中으로 하향, A가 경쟁.

**최종**: 옵션 **B**, **신뢰도 上**(in-scope). **결정룰**: *스택→스킬을 repo 컨텍스트로 결정론적·강제 바인딩하면 B(상); 바인딩이 재량적이거나 한 세션이 다(多)스택을 오가거나 권한이 하드 보안경계면 A.*
