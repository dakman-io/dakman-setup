회원가입 · 인증 스키마 ERD 샘플

dakman 글로벌 B2C 기준 — 정체성≠인증수단 분리, core/edge 구분, 상태기계, 단일 진실 출처, 제약=가드레일

Core — 정체성·권한. 네가 설계·지킴. 정규화, 바꾸기 어려움 Edge — 세션·토큰·로그. append-only/휘발성. AI 자유, 버려도 됨

이 스키마가 박고 있는 설계 결정

① 정체성 ≠ 인증수단

users는 "누구인가"만. "어떻게 로그인하나"는 auth_identities로 분리. 덕분에 한 유저가 비밀번호+구글+애플을 동시에 갖고, 비번 없는(소셜전용) 유저도 자연스러움. 비번 컬럼을 users에 박으면 이게 다 막혀.

② status = 상태기계

pending → active → suspended → deleted. 기능마다 status를 자유롭게 찌르지 말고 허용된 전이만. 회원가입은 곧 "이 엔티티의 생애주기 시작"이라 여기가 불변식의 핵심.

③ core vs edge

Core(users·identities·roles)는 정규화·신중. Edge(sessions·tokens·events)는 휘발성/append-only라 AI가 자유롭게. 같은 엄격함을 둘에 다 쓰지 않는 게 속도의 비결.

④ 단일 진실의 출처

"이메일 검증됨"의 진실은 users.email_verified_at 한 곳. auth_tokens는 *절차*일 뿐 상태가 아님 — 토큰 소비 후 users를 갱신. 검증 상태가 두 곳에 살면 드리프트 = 사고.

⑤ 제약 = AI가 못 깨는 가드레일

email UNIQUE, (provider, provider_uid) UNIQUE, 전 FK에 ON DELETE CASCADE. 기능 코드가 틀려도 DB가 막음. 데이터 흐름 규칙을 코드 아니라 스키마가 강제.

⑥ soft delete = 가역성

탈퇴는 행 삭제가 아니라 status=deleted + deleted_at. 실수·복구·법적 보관 대응. 비가역(진짜 DELETE)을 가역으로 바꾸는 우리 1원칙의 실제 적용.

⑦ 토큰은 해시만, 원문 금지

sessions.refresh_token_hash·auth_tokens.token_hash — 평문 저장 X. DB 유출돼도 토큰 재사용 불가. 글로벌 B2C에선 기본값.

⑧ auth_events = 감사 로그

append-only edge 테이블. 가입·로그인·실패를 기록 → 이상탐지·디버깅·컴플라이언스. core를 더럽히지 않고 관측성 확보.
