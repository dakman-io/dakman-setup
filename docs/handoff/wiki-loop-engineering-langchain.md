# 루프 엔지니어링 — 에이전트가 언제 '시스템'이 되는가 (LangChain)

> ✅ **ingest·verify 완료 (dakman-wiki, 2026-07-05, PR #23)** → 정본 = `dakman-wiki: wiki/loop-engineering-langchain.md (verified)`. 이 핸드오프 문서는 그 소스(역사 아티팩트).
> ⚠️ **출처 정정**: verify에서 LangChain 원문 대조 결과 — **4루프·harness·create_agent·trace = LangChain 1차** 확인. 그러나 **'완료=판정'·'검증수요↑'·승인 피로/비대칭·'프롬프트 이후'는 LangChain 원문에 없음 = 율무커피 2차 정리의 가필**. 아래 본문은 1차/2차가 섞여 있으니, 인용 시 정본 위키 페이지(1차/2차 분리 라벨)를 쓸 것. 2차 해석을 "LangChain이 말했다"로 단정 금지.

> **핵심 thesis**: 에이전트가 현실 업무를 자동화하려면 좋은 *모델*만으론 부족하고, 작업군에 맞게 설계된 **harness**(제어계)가 필요하다. 그 harness의 본체 = **루프**(단순 반복문이 아니라 *판단의 위치를 정하는 구조* — 무엇을 자동화·검사·재시도·사람승인할지 배치). **"완료는 모델의 발화가 아니라 시스템의 판정"**이 관통 명제.
> ⚠️ **출처 등급**: LangChain 블로그가 1차(신뢰 높음), 이 정리는 한국어 2차 경유 → `secondary`·미검증. verify 시 LangChain 원문 대조 권장.

## 4개 루프 (LangChain 프레임)

에이전트 시스템 = 안쪽→바깥으로 4개 루프의 중첩. 첫 3개는 *일을 자동화*, 네 번째는 *개선을 자동화*.

| # | 루프 | 하는 일 | 핵심 |
|---|------|---------|------|
| 1 | **Agent loop** (행위의 발생) | 모델이 맥락 읽고→행동 정하고→도구 호출→결과 읽고→다시 판단, 완료까지 반복(`create_agent`) | **자동화의 최소 단위지 신뢰의 최소 단위가 아님.** "수행했다" ≠ "올바르게 끝냈다". 도구 가진 에이전트의 오판 = 파일·PR·데이터·비용의 실제 변경(위험 반경 확대) |
| 2 | **Verification loop** (검증이라는 외부 시선) | 결과물을 곧바로 안 믿고 채점자(결정론 규칙·rubric·다른 LLM)를 둠. 미달이면 피드백→재시도 | ★ **검증은 가능하면 모델의 자신감과 *독립된 경로*.** 테스트·타입체크·diff 제한·policy·sandbox·권한·비용·데이터 무결성. "좋은 모델일수록 검증 수요가 *늘어난다*"(성능↑ = 통제장치 대체재 아니라 수요 증가). 신뢰 = 개인 능력 아니라 **절차의 중복성**(peer review·redundant check·승인 분리) |
| 3 | **Event-driven loop** (조직의 일부가 됨) | 새 문서·웹훅·cron·Slack 메시지에 에이전트가 반응(사람이 매번 호출 안 함) = "채팅창 비서 → 워크플로의 구성원" | 트리거 추가처럼 보이나 조직론적으론 큼. **핵심은 실행 능력 아니라 실행 *조건*** — 어떤 이벤트가 충분한 원인인가·큐잉/사람확인·중복실행 방지·실패 시 재시도/보류/롤백. "호출이 자동화되면 실패도 자동화된다" → 실행빈도↑ 해도 실패 누적 안 되는가 |
| 4 | **Hill climbing loop** (흔적을 학습 재료로) | ★가장 중요. 실행마다 남는 **trace**(무엇을 했나·도구·실패 단계·grader 피드백)를 분석 에이전트가 읽어 **프롬프트·도구·grader 등 harness 구성을 개선**. 바깥 루프가 안쪽 루프를 수정 | 단순 자동화(같은 일 반복) → **반복 결과로 반복 구조 자체를 바꿈**. "trace 쌓기 ≠ trace로 시스템 고치기"(관측 vs 학습). 에이전트 운영 = 실험실(실행=실험, trace=실험노트, grader=관측장치, harness 변경=다음 실험조건). "잘 되는 프롬프트 찾기 → 성능이 누적되는 실험체계 만들기" |

## 관통 원칙

- **완료는 발화가 아니라 판정.** "완료했습니다"는 사용자 안심용 문장 — 운영에선 **시스템의 판정**(테스트 통과·변경범위 맞음·정책 미위반·승인 완료·trace 남음·복구경로 존재)이어야. "모델의 문장이 아니라 시스템의 *상태*가 완료를 말한다." 좋은 제품은 그 판정을 모델에게 맡기지 않는다.
- **인간은 루프 밖으로 사라지지 않는다.** 자동화 ≠ 인간 제거. 인간 검토는 모든 루프에 들어갈 수 있다(민감 도구 호출 전 승인·민감 워크플로 인간 grader·결과 반환 전 승인·harness 개선 배포 전 리뷰). **금융·DB 같은 민감 행위엔 실시간 인간 검토 필수.**
  - ⚠️ **나쁜 human-in-the-loop = 책임 전가·피로 생산.** 하루 수십 번 승인 팝업 = 판단 요구가 아니라 피로 장치 → 사람은 결국 "더 이상 읽지 않고" 누른다(rubber-stamp). **좋은 개입 = 드물고·비대칭적이고·정보 충분.** 모든 걸 묻지 말고 *되돌리기 어렵거나·정책 민감하거나·모델이 확신 못 하는* 지점에서만. "승인할까요?" 대신 **무엇이·왜 바뀌고·실패 시 영향**을 보여줘야. 인간 판단 = 귀한 자원 → 아끼는 방향 설계.
  - "자동화 성숙도 = 사람이 얼마나 *적게* 등장하느냐가 아니라, *등장해야 할 순간에 정확히* 등장하는가."
- **품질은 답변이 아니라 궤적(trace)에서.** 단발 답변 평가 → 궤적 평가(관찰 순서·도구·가설·실패 감지·멈춤·남긴 것). 성공률·비용·latency·tool call 수·실패 복구율 다 필요하나 **가장 중요 = 실패의 *해석 가능성*.** 왜 실패했는지 모르는 에이전트는 개선 불가 → 성숙 불가.
- **loop engineering = 제품론이자 조직론.** 어느 채널에서 호출·어떤 라벨에 반응·어떤 권한·누가 실패를 보나·어떤 trace 저장·어떤 기준으로 프롬프트 바뀌나·어떤 변경은 리뷰 없이/사람 승인. = 기술 설정이자 **조직의 의사결정·책임 회로**. "에이전트 조직은 모델 도입보다 먼저 *책임의 회로* 설계"(누가 요청·승인·검증·실패 학습했나 — 흐리면 생산성 아니라 책임을 증발).
- **프롬프트 엔지니어링 이후.** 프롬프트는 안 사라지나 중심에서 밀림 — "모델에게 무엇을 하라" 말할 뿐, 루프는 "그 말을 어떻게 감시·언제 반복·어떻게 멈춤·어떤 흔적을 다음 설계에 반영"을 정함. 모델 성능↑ → 단발 프롬프트 차별성↓ → **남는 차이 = 운영 계층**(누가 더 정교히 평가·안전히 권한분리·빠르게 trace서 학습·좋은 이벤트조건·사람 판단 안 낭비).
- 인상 구절: "AI 제품 성숙도는 데모에서 안 드러난다(데모는 늘 잘 됨) — **세 번째 실패 이후** 드러난다: 실패가 기록되나·분석되나·harness를 바꾸나·바뀐 harness가 다음 실패 모양을 바꾸나." / "경쟁력 = 누가 더 많이 돌리느냐가 아니라 **돌린 뒤 무엇이 남는가**(로그만 남는 조직 vs 실패가 남는 조직 vs 규칙이 남는 조직)." / "자율성보다 정확한 단어 = **폐회로**(행위→검증→수정→행위조건 변경)."
